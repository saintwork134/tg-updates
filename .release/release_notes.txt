TG Mass Sender v2.8.55

Corrections:
- A fresh activity label no longer hides an account with failed attempts and no accepted sends.
- Low-activity detection respects computed warnings even when an older base severity is OK.
- Summary warnings and detailed account diagnostics use the same diagnostic snapshot.
- Sending-only clients opt out of unsolicited SDK update streams; monitoring/auth defaults are unchanged.
- Network recovery attempts are counted independently of account errors, without double counting.
- An exhausted connection recovery ends the cycle with a network status, not a generic three-hour account rest.
- Network retries use bounded backoff (60, 120, 240, 480, 600 seconds) without changing stored account restrictions.
- Initial and refreshed dialog lists and Saved Messages retrieval have 30-second deadlines.
- Account restriction errors from dialog refresh propagate to the existing account-state handler.
- Session guards and client registry entries are released even if cleanup is cancelled again.
- Verified bans, session revocations, Premium state and manual rest keep precedence over network status.

Diagnostics:
- Each operation has a run id, operation id, hashed account reference, cycle, phase and elapsed time.
- Operation timestamps explicitly use UTC; reports identify the host-log and database timezones.
- Errors include exception type, numeric RPC/OS codes, recognized account state and server wait seconds.
- Message ids and chat ids correlate acceptance and deletion checks; message contents are never recorded by telemetry.
- New telemetry omits credentials and arbitrary exception/request text.
- Operation counters are aggregated; active detail storage is capped at 256 entries without per-message history.
- Effective engine settings and effective per-chat delays are recorded separately from edited UI settings.
- Resource samples include working set, peak working set, private memory, CPU time, loop lag and per-client queues.
- A protective stop reacts to update queues of 10000 entries or excessive process memory.
  The sampled memory threshold is 25 percent of installed RAM, with a 1-4 GiB threshold range.
  This is a protective stop, not a hard allocator ceiling; automatic restart is not performed.
- Support reports include operation_diagnostics.json and report_scope.json, including truncated log indicators.
- Reports capture presence, pacing, typing, batching and startup-check settings, without authentication secrets.
- Account CSV/JSON includes a trace reference matching operation logs.
- Log rotation during report collection does not fail the whole export.

Validation is offline with fake clients and temporary databases. Telegram FloodWait and other server restrictions
remain enforced. A real long-running resource test is still required before claiming that all memory growth is resolved.
